How It Works

From config to production in three steps

The same loop runs on a laptop, in CI, or across a fleet of runners.

01

Write and initialize

Define resources in main.hcl and run nimbus init to fetch providers and configure your state backend. Everything is plain text in version control.

02

Plan and review

nimbus plan produces an exact diff of every create, update, and delete. Attach it to a pull request so reviewers approve the change, not the intent.

03

Apply and verify

nimbus apply executes the approved plan with state locking and automatic rollback on failure. Post-apply checks confirm drift stays at zero.

FAQ

Common questions

Answers from the engineering team. More detail lives in the docs.

How does Nimbus handle state security?expand_more
State is encrypted at rest and in transit on every supported backend. Team and Enterprise tiers add automatic locking, full version history, and role-based access so only approved applies can write state.
Can I migrate existing infrastructure into Nimbus?expand_more
Yes. The nimbus import command reads live resources and generates matching configuration. Most teams import an existing environment in an afternoon and reconcile drift from the generated plan.
Which cloud providers are supported?expand_more
AWS, Google Cloud, Azure, and over 200 community providers covering Kubernetes, databases, DNS, and SaaS tooling. Providers are versioned independently, so upgrades never force a full migration.
